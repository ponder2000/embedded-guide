DIAGRAM 01

Struct padding, made visible

The compiler inserts invisible bytes so every member sits on an aligned address. A uint32_t after a uint8_t isn't at offset 1 — it's at offset 4, with 3 ghost bytes in between.

The rule: a type of size N must sit on an address divisible by N. For register-overlay structs, every field is uint32_t, so they're already naturally 4-aligned — no padding sneaks in, and the struct offsets match the datasheet exactly. Mix sizes and ghosts appear.
DIAGRAM 02

Where your code and data actually live

Two physical memories on the chip. Flash keeps things across power-off; RAM is fast but blank at boot. Each section of your program has a fixed home.

Why .bss costs no flash: if a global is zero-initialized, its value doesn't need to be stored anywhere persistent — startup code just zeroes that RAM region in a loop. Nonzero initial values, by contrast, must live in flash and get copied to RAM.
DIAGRAM 03

How your source becomes firmware

From C files to bytes burned into the chip — four transformations, each one shedding abstraction.

The split between .elf and .bin: .elf is what your debugger loads (it has symbol/address info for breakpoints). .bin is the raw image you actually write to flash. Same program, two packagings — one annotated, one stripped.
DIAGRAM 04

Boot, in five moves

Power-on. There's no OS, no main, no initialized variables. Watch what hardware and startup code do — in order — to build the world your C program expects.

The whole "C runtime" is just two loops: copy .data from flash to RAM, then zero .bss. After that, the world matches what your C code expects (initialized globals have their values; uninitialized ones are zero) and main can run.
DIAGRAM 05

Why volatile exists, in one picture

The compiler's optimizer can cache a value in a CPU register and never re-read memory. Fine for normal variables. Fatal for hardware registers and ISR-shared state.

Volatile is a message to the optimizer, not safety machinery. It says: re-read this from memory every time, never cache. It does not make compound operations atomic — see Diagram 08.
DIAGRAM 06

Bit operations on a register

A 32-bit register is 32 independent switches. The four primitives — set, clear, toggle, read — touch only the bits you name.

Always use 1U not 1: shifting a plain (signed) 1 into bit 31 is undefined behavior. 1U makes it unsigned, which wraps cleanly and is well-defined.
DIAGRAM 07

Interrupts pass through two gates

A hardware event has to make it past the peripheral's mask, then the NVIC's mask. Only then does it reach the CPU and trigger your ISR via the vector table.

The #1 beginner bug: only one gate is open. Either the peripheral interrupt-enable bit is missing (event never asserts an IRQ line), or the NVIC isn't told to let IRQ #N through (event asserts but is masked). Always check both.
DIAGRAM 08

The race volatile can't fix

counter++ is three machine instructions, not one. If an ISR fires between them, you lose a count — even though both sides are volatile.

Both incremented; result is +1, not +2. Fix: either bracket the RMW with __disable_irq()/__enable_irq() (a critical section), use an atomic primitive, or design so only one side writes the shared variable.
DIAGRAM 09

The life of one UART byte

Watch the byte 'A' travel from the wire, through the peripheral, into a ring buffer, where main code eventually consumes it.

WHY THE RING

The ISR is fast and uncontrollable; main is slow and steady. The ring buffer decouples them — producer-consumer pattern with single-writer indices, so no critical section is needed even with both sides volatile.

ISR DISCIPLINE

The ISR only shovels: read DR, store in buffer, advance head. No printf, no parsing. All real work happens in main, off the interrupt path.

This pattern generalizes to every peripheral. SPI, I²C, ADC, CAN — same shape: hardware deposits data into a peripheral register, an ISR moves it into a software buffer, main code consumes it at its own pace.
