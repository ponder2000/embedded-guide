SECTION 01

Stop asking — let the hardware tap you on the shoulder

There are two ways for your CPU to find out that a button was pressed or a byte arrived. It can ask, over and over, forever — that's polling. Or it can get on with other work and trust the peripheral to interrupt it the instant something happens. The second way is almost always the right one.

Polling means a tight loop that reads a status bit and spins until it flips: while (!(USART1->SR & USART_SR_RXNE)) { }. Simple, but the core burns every cycle checking a thing that hasn't happened yet — and it can't sleep, so the battery drains for nothing.

With an interrupt you arm the peripheral once, then walk away. When the event fires, the CPU drops what it's doing, runs a short handler, and resumes. Between events it can run useful background code or enter a low-power sleep state and wake on the very signal it cares about.

The trade: polling is dead simple and predictable, so it's fine for a quick check or a tight real-time loop you fully own. But for anything bursty, rare, or battery-sensitive — a keypress, an incoming byte, a timer tick — interrupts let the CPU stop wasting cycles and actually rest.
SECTION 02

The NVIC routes the signal, the stack remembers

On a Cortex-M, every interrupt funnels through one piece of hardware: the NVIC, the Nested Vectored Interrupt Controller. It tracks which interrupts are pending, decides which one wins when several arrive, and lets a more urgent interrupt preempt one already running — that's the "nested" part.

Two ideas do the heavy lifting. The vector table is a fixed array at the start of flash: slot N holds the address of the handler for IRQ N. When IRQ N fires, the hardware reads slot N and jumps there — no if/else dispatch, the lookup is wired in. And each interrupt has a priority number, where lower means more urgent. A priority-1 timer can interrupt a priority-3 UART handler mid-flight; the UART resumes once the timer's handler returns.

All of the stacking and unstacking — pushing PC, PSR, and the caller-saved registers, then restoring them — is done by the Cortex-M hardware, not by your code. That's why you can write an ISR as an ordinary C function with no special prologue: the silicon already saved everything that mattered.
SECTION 03

Keep the ISR short — and mind the shared data

An ISR steals the CPU from whatever was running. The longer it stays, the more it delays main and any lower-priority interrupt waiting behind it. So the rule is brutal and simple: do the urgent minimum, then get out.

The clean pattern is a handoff. The ISR clears its flag, records what happened, and sets a single volatile variable. Main polls that flag at its own pace and does the slow work — parsing, math, anything that doesn't have to happen right now.

Two traps wait here. First, anything an ISR and main both touch must be volatile, or the compiler may cache it in a register and never see the ISR's update. Second, volatile alone does not make access atomic: count++ is read-modify-write, three instructions, and an interrupt landing in the middle corrupts it. For multi-byte shared state, either keep one side a sole writer or briefly disable interrupts around the access.

The discipline: an ISR that's short, clears its own flag, and only sets a volatile flag for main is the pattern that keeps embedded systems responsive and bug-free. Long handlers and unguarded shared variables are the source of the nastiest, hardest-to-reproduce bugs in firmware — set a flag, do the work in main.
