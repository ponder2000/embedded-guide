SECTION 01

A scheduler is a tool, not a requirement

A real-time operating system organizes firmware into independently scheduled tasks. It can make multiple activities easier to express, but it adds stacks, synchronization, scheduling rules, and new failure modes. A small nonblocking main loop may still be the clearest design.

Start with bare-metal event loops, interrupts, and health supervision. Real-time means meeting defined timing constraints, not merely running fast. Using an RTOS does not by itself prove a deadline will be met.

SECTION 02

Let waiting tasks stop competing

In a typical single-core priority-based preemptive design, the scheduler runs the highest-priority ready task. A task blocked on a queue, notification, or timeout is not ready. When its event arrives, it becomes ready; it runs when scheduling rules allow.

A high-priority loop that continuously polls an empty queue can starve lower-priority work. Prefer a blocking wait with a bounded timeout where appropriate. Equal-priority time slicing, if configured, does not rescue lower-priority tasks from a permanently ready higher-priority task. Priority number conventions differ between kernels and interrupt controllers: check what a larger number means.

Periodic work should use the kernel's periodic-delay facility when appropriate rather than adding a relative sleep after every execution; relative delays accumulate execution-time drift. Tick frequency, rounding, interrupt latency, long critical sections, and other ready tasks affect actual timing. A delay is not a precise hardware waveform generator.

Budget before prioritizing: identify periods, worst-case execution time, deadlines, and acceptable blocking. Assigning every task a high priority creates no additional CPU capacity.
SECTION 03

Communicate with ownership rules

For a sensor → logger pipeline, let the sensor task produce messages and the logger task own the output peripheral. A queue gives a bounded place to transfer work. Define capacity and a full-queue policy: wait within a deadline, reject/drop with a counter, or replace an old value if only the newest measurement matters.

In FreeRTOS, queues copy the configured item bytes. Queuing a pointer copies the pointer, not the pointed-to data. Its buffer must remain valid and its ownership explicit until the receiver finishes. Large messages may be better represented by a fixed buffer pool with a documented return path.

A mutex protects a shared resource and has an owner. In kernels that support it, priority inheritance can reduce priority inversion when a high-priority task waits on a resource held by a lower-priority task. It does not eliminate deadlocks, make long lock holds safe, or replace a consistent lock order. A binary semaphore is not automatically a mutex with inheritance.

ISRs must use the kernel's documented interrupt-safe APIs and obey the port's interrupt-priority restrictions. In FreeRTOS those APIs commonly have an FromISR suffix and cannot block. Request a context switch using the port's prescribed mechanism when required; never take a task-owned mutex from an ISR.

SECTION 04

Make resource limits visible

  • Stacks: every task needs a bounded stack. Check API units—FreeRTOS task stack depths are expressed in StackType_t elements, not universally bytes. Measure high-water marks under representative stress and retain margin.
  • Memory: choose static allocation or a deliberate allocation strategy. Handle allocation failure; do not assume an embedded heap is unlimited.
  • Overload: track missed deadlines, queue saturation, buffer exhaustion, and dropped messages.
  • Recovery: supervise critical tasks' useful progress, not just whether a scheduler tick continues.

Test delayed consumers, queue-full conditions, a stalled high-priority task, and missing events. Start with two tasks and one explicit handoff, not a task per function. Keep the nonblocking heartbeat from the first project as a baseline for deciding whether an RTOS makes your design clearer.

Official references: consult FreeRTOS documentation and the FreeRTOS kernel source for task states, queues, mutexes, allocation, and your selected Cortex-M port. Pin the kernel version and configuration used by your project.
