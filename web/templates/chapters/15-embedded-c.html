SECTION 01

Choose the width before the operation

Bare-metal C makes storage visible. A hardware register has a documented width; your variables and masks should match it. Unlike many application languages, C does not give every integer the same range, and signed overflow is undefined behavior.

Include <stdint.h> for uint8_t, uint16_t, and uint32_t: unsigned integers of exactly 8, 16, and 32 bits, where the implementation provides them. Plain int is not necessarily 32 bits. Converting an integer to uint8_t wraps modulo 256; arithmetic on small integer types usually first promotes them to int. Distinguish the intermediate calculation from the value finally stored.

#include <stdint.h>

uint8_t count = 255;
count = (uint8_t)(count + 1);  /* stores 0 */
unsigned n = 31;               /* require 0 <= n < 32 */
uint32_t mask = UINT32_C(1) << n;

Use an unsigned mask, not a signed 1 << 31. Never shift a 32-bit operand by 32 or more, and never use a negative shift count. The explorer keeps the count in range and displays JavaScript's bitwise result as unsigned using >>> 0; JavaScript's shift-count wrapping is not a C rule.

SECTION 02

An address is not the value stored there

A pointer identifies a location and a pointed-to type. Dereferencing it accesses the object at that location. For ordinary RAM, &value obtains an address; *pointer accesses its contents. Pointer arithmetic advances in objects, not necessarily bytes.

/* Illustration only: use your device's vendor header. */
volatile uint32_t * const control =
    (volatile uint32_t *)(uintptr_t)UINT32_C(0x40000000);
uint32_t snapshot = *control;

A memory map tells you which addresses select RAM, flash, or memory-mapped I/O (MMIO). The example address is device-specific fiction, not a safe register to probe. Integer-to-pointer conversion depends on the target implementation. A valid access also requires the correct alignment, register width, peripheral clock, and permissions. A random dereference may fault or change hardware state.

Here volatile qualifies the register being accessed; const prevents reassigning the pointer itself. Volatile accesses must follow the implementation's hardware-access rules rather than being optimized away as ordinary unused reads. They do not automatically provide CPU memory barriers or cache coherence. Prefer the vendor's typed register definitions and documented access sequence.

SECTION 03

Update a field, not its neighbors

For an ordinary read/write register, clear the target field and insert the new value. OR alone cannot replace a field: a previous one bit would survive when the new value needs zero.

/* Only for an ordinary R/W register; mode is 0..3. */
uint32_t field_mask = UINT32_C(3) << 4;
uint32_t old = *control;
uint32_t mode = 2;
*control = (old & ~field_mask) | ((mode << 4) & field_mask);

The mask covers bits 5:4. Inverting it keeps unrelated bits from the snapshot, while the final AND confines the inserted value. This is a read-modify-write, not one indivisible action. If an interrupt, another core, or hardware changes the register between the read and write, the old snapshot can overwrite that change.

Read the register's access description before applying this idiom. Write-one-to-clear (W1C) status bits clear when written as one: reading status and writing it back can accidentally acknowledge every pending event. Clear only the intended documented W1C bits by directly writing their mask. Read-only, read-to-clear, mixed-access, and reserved bits require their own rules. Use dedicated SET/CLEAR or set/reset registers when available; these avoid a software read-modify-write for supported operations. They still require the device manual's prescribed values and ordering.

First classify the register. A mask preserves neighbors only when the register semantics and concurrency assumptions make that read-modify-write safe. C bit-field declarations are not a portable substitute for explicit hardware masks.
SECTION 04

Layout and sharing need separate contracts

Arrays store elements contiguously, with a stride of sizeof element. Structures preserve member order but can include alignment padding between members and at the end. They are not packed by default.

struct Sample {
    uint8_t tag;
    uint32_t ticks;
};
struct Sample samples[2];
/* sizeof samples == 2 * sizeof(struct Sample) */

Use sizeof and offsetof (from <stddef.h>) to check actual layout. Endianness determines byte order within multi-byte integers, not member order. Do not transmit or persist raw structs as a portable format; serialize fields explicitly. Packing extensions can introduce unaligned accesses and are not a universal fix.

Sharing with an ISR adds another contract. A volatile flag can support a target-documented polling pattern, but does not guarantee atomic access, prevent lost events, or publish accompanying nonvolatile data safely. Even flag++ is a read-modify-write. C11 _Atomic provides atomic operations and memory-order tools, but ISR use requires toolchain support and operations verified lock-free and interrupt-safe; a hidden library lock can deadlock. Otherwise use a short platform-approved critical section, restoring the previous interrupt state. A boolean also merges repeated events: use a protected counter or queue when every event matters.
