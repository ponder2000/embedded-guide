SECTION 01

Your computer builds; the board runs

The host is your development computer. The target is the microcontroller. Building firmware on one machine does not mean that machine can execute it: an STM32F401 needs Arm instructions, not your laptop's native program format.

A cross-toolchain runs on the host but produces code for the target. STM32CubeIDE supplies a supported Arm toolchain and integrates project generation, building, programming, and debugging. Start with its board selector for NUCLEO-F401RE, not a random project's compiler command or linker settings.

Preprocessing expands headers and macros; compilation translates C into assembly; assembly creates machine-code object files. Linking combines those objects with libraries and resolves references between them. A missing header is not the same failure as an undefined function at link time: identify the failing stage before changing settings.

SECTION 02

Give the program a home and a beginning

Machine instructions alone are not a bootable application. The linker script describes the selected chip's flash and RAM, while startup code prepares the C environment before calling main().

Startup normally supplies the vector table and reset handler, copies initialized data into RAM, and clears zero-initialized storage. The linker places these sections into appropriate memory regions. Keep the generated startup file and linker script matched to the exact device; copying them from another STM32 can produce a successful build that cannot boot.

The build's ELF contains sections, address information, and, in a debug build, symbols connecting instructions to source lines and variable names. A raw binary contains bytes but does not describe where to program them. Never guess a binary's destination address: use the project's documented memory layout. For this lesson, let CubeIDE program its generated ELF.

Hands-on: build the generated board project. Find its ELF, linker script, startup file, and build console. Record the first error if building fails; later errors may merely be consequences. Inspect the memory-usage summary before adding features.
SECTION 03

Flash through a debug probe

Flashing writes the application into nonvolatile memory. A debug probe bridges USB on your computer to the target's debugging interface; it is not simply a serial cable.

On a stock NUCLEO-F401RE, use the onboard ST-LINK USB connector and a data-capable cable. Check the board manual's jumper and power configuration. No external probe wiring is needed for this first exercise.

For a separate probe, SWD typically needs SWDIO, SWCLK, common GND, and target-voltage reference; reset may also be useful. Voltage reference is not guaranteed to supply power. Check both manuals and voltage compatibility before connecting anything.

Select the project's ST-LINK debug configuration in CubeIDE and launch Debug. Accept programming only for your connected practice board. A virtual COM port, if available and routed correctly, carries UART traffic; opening it neither flashes firmware nor automatically makes printf work.

SECTION 04

Stop, inspect, then resume

Use a debug build and configure a breakpoint at main(). Reset or restart through the debugger, verify that execution stops there, then step past generated initialization. Watch a variable that is in scope; resume to let the application run normally. A halted processor cannot blink an LED.

Optimization can remove variables, reorder operations, and make source stepping surprising. Use the project's debug-friendly optimization setting rather than adding volatile everywhere. Breakpoints also disturb timing; peripherals and watchdogs may continue unless specifically configured to freeze.
