SECTION 01

Firmware does not require an operating system

Bare-metal firmware runs directly on the microcontroller, without an operating-system scheduler. Libraries, vendor drivers, startup code, and language runtimes can still be part of that firmware.

Learning objectives: trace reset to application code, recognize equivalent register writes in C, Rust, and Zig, and distinguish an event loop from interrupt execution.

For a normal Cortex-M reset, hardware obtains the initial main stack pointer (MSP) from the first vector-table word and the reset-handler address from the second. The device's boot selection determines which memory supplies those vectors. A correctly formed handler address indicates Thumb execution. Hardware does not automatically initialize every language variable or call main.

Startup normally copies initialized .data from its flash load image into SRAM and zeros .bss. It may call SystemInit, initialize language support, and then enter the application. Hook names and ordering vary: some vendor startup calls SystemInit before copying data. Never assume globals are ready inside an early hook. Rust runtime crates and Zig platform startup can provide equivalent setup; neither language removes the need for it.

SECTION 02

See what belongs in the image

A firmware build needs executable code, a vector table, and a memory layout agreed upon by startup and the linker. A linker script, or equivalent linker configuration, places sections in the device's flash and SRAM. The ELF can retain symbols for debugging; the programmed image must contain the bytes needed at boot.

Instructions and constant data commonly stay in flash. Initialized writable variables have two locations: initial bytes stored in flash and a runtime address in SRAM. Zero-initialized storage needs SRAM space but normally no matching block of zero bytes in flash. The stack needs reserved, correctly aligned RAM. A heap is optional: using static storage and stack variables requires no dynamic allocator. Allocation needs explicit allocator/runtime configuration and enough memory.

Check the link map against the exact device capacities. An address compiling successfully does not prove it is mapped, powered, or safe. A wrong vector location, stack bound, or data-copy range can fail before any LED code executes.

SECTION 03

One hardware action, three languages

These equivalent snippets are not standalone runnable binaries. They apply only to STM32F401, after startup, GPIOA clock enable, and PA5 output configuration are complete. GPIOA BSRR is a 32-bit register at 0x40020018. Writing bit 5 sets PA5's output latch; it does not configure the pin or generate a blink.

C: include the fixed-width integer definition, then perform a volatile store inside your application.

#include <stdint.h>

/* Inside an initialized application function: */
volatile uint32_t * const bsrr =
    (volatile uint32_t *)0x40020018u;
*bsrr = (uint32_t)1u << 5;

Rust: the raw pointer operation requires an unsafe block; the programmer must establish address validity and hardware preconditions.

// Inside an initialized application function:
unsafe {
    core::ptr::write_volatile(
        0x40020018usize as *mut u32,
        1u32 << 5,
    );
}

Zig: a volatile pointer requests the hardware-visible store. Toolchain versions and platform startup APIs vary; this supplies no startup implementation.

// Inside an initialized application function:
const bsrr: *volatile u32 = @ptrFromInt(0x40020018);
bsrr.* = @as(u32, 1) << 5;

All three request a 32-bit volatile write. Volatile is not a general atomicity, race-prevention, or memory-ordering guarantee. Required barriers and synchronization depend on the hardware and concurrency. BSRR's atomic set/reset action comes from the peripheral, avoiding CPU read-modify-write of the output register; it does not protect unrelated shared state.

SECTION 04

Run an event loop; respond to interrupts

A simple application repeatedly polls inputs, advances small state machines, and updates outputs. An enabled interrupt can suspend that foreground code, run its handler (ISR), and return. This is not an OS thread switch. Keep handlers short and coordinate shared data explicitly. An RTOS is optional when scheduling requirements justify one.

The foreground loop can be written as for (;;) { app_step(); } in C, loop { app_step(); } in Rust, or while (true) { appStep(); } in Zig. Those step functions are application-defined placeholders: each should do a small, bounded piece of work and return, not wait forever for an input.

Self-check and answers

Does bare-metal mean no libraries? No: it means no OS is required. Does the CPU zero .bss automatically? No: startup software normally does. Does a BSRR write start a thread? No: it requests a GPIO hardware action.
