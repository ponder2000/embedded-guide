SECTION 01

Sleep is a feature, not a failure

A microcontroller that runs flat-out all day is a battery's worst enemy. The whole craft of low-power design is knowing how little of the chip you can keep awake — and for how long — while still waking the instant something happens. Each deeper mode trades wake-up speed and retained state for a smaller current draw.

The trick is that the chip does almost nothing useful in software to go to sleep: it executes a single instruction — WFI, "Wait For Interrupt" — and the core simply stops fetching. It stays stopped, drawing a trickle, until a peripheral or pin raises an interrupt. Then the core wakes exactly where it left off, services the event, and dives back under. A well-written sensor node spends 99.9% of its life in Stop or Standby and is awake only in the milliseconds it takes to read a value and shout it over the radio.

The dial you're turning: deeper modes power down more of the silicon, so current falls from milliamps to nanoamps — but you give up retained state (RAM may be wiped) and pay a longer wake-up latency. Choosing a mode is choosing how patient your application can afford to be.
SECTION 02

What volatile protects you from

The compiler's optimiser is brilliant and ruthless: if nothing in your code writes to a variable inside a loop, it will read it once, stash it in a CPU register, and never touch memory again. For an ordinary counter that's a gift. For a hardware register or a flag an interrupt flips behind your back, it's a silent hang.

You declare the keyword right at the pointer to the hardware: volatile uint32_t *FLAG = (volatile uint32_t *)0x40020014;. The volatile qualifier is a promise the compiler must keep — it says this address can change at any moment for reasons outside this function, so emit a fresh load from memory on every access and never fold the reads away. Use it for every memory-mapped register and every variable an ISR shares with your main loop.

What volatile is and isn't: it is a message to the optimiser — re-read from memory, never cache. It does not make access atomic and it does not protect against races; for that you still need to disable interrupts or use proper atomics around multi-step updates.
SECTION 03

The code that runs before main()

You write main() and assume your variables already hold their initial values and your zero-initialised globals really are zero. On bare metal, nothing is free — a small hand-written reset handler has to build that world out of raw flash and blank RAM before your first line ever executes.

This startup code — the C runtime, often called crt0 or the reset handler — is what makes C feel like C on bare hardware. It loads the stack pointer from the top of the vector table, copies the .data section (your globals with explicit initial values) out of flash into RAM, writes zeros across the .bss section (everything declared but uninitialised, or set to zero), and only then branches to main(). Skip those steps and your "global = 42" would be garbage, and your zeroed array would be full of whatever the RAM held at power-on.

And notice the while (1) that wraps every embedded main(). On a desktop, returning from main hands control back to the operating system. Here there is no operating system — return from main and the CPU falls off the end of the world into undefined behaviour. So you loop forever, doing your work or sleeping on WFI between interrupts.

The whole journey, in one breath: we started with bits — patterns of voltage that mean numbers. We watched a single bit flip a register and a register switch a real pin. We saw the chip boot, copy itself into being, and call main(); talk to the world over UART, SPI and I²C; respond in microseconds to interrupts; and finally sleep at nanoamps, waking only when needed. "Set bit 5 of the GPIO output register to turn on the LED" is no longer a spell — it's a sentence you can read down to the silicon. That blinking chip on your bench is just bits, kept honest by volatile, carried by a runtime you now understand. Go build something.
