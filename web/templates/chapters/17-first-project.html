SECTION 01

One board, one visible success

Build a heartbeat on a NUCLEO-F401RE using STM32CubeIDE and the generated STM32 HAL project. The first goal is modest: make the onboard user LED change predictably, then prove that your own firmware survives a reset.

You need the board, a data-capable USB cable matching its onboard ST-LINK connector, and the vendor-supported development tools. Leave breadboards and external circuits disconnected. Consult ST's UM1724 Nucleo-64 manual and the schematic for your board revision, identified by its markings. On NUCLEO-F401RE, user LED LD2 uses PA5 and user button B1 uses PC13; verify those connections rather than transferring assumptions from another Nucleo.

Connect only the ST-LINK USB cable using the manual's normal USB-power configuration. Identify the power indicator separately from LD2: a steady power light proves power, not that your application works.

SECTION 02

Generate the foundation, then blink

In CubeIDE, create an STM32 project through the board selector and choose NUCLEO-F401RE. Accept board initialization where offered, install the required STM32F4 firmware package, and inspect the generated configuration. Menu wording varies by version. Confirm PA5 is a push-pull GPIO output and that the generated system-clock configuration is valid; do not copy clock settings from an unrelated board.

Generate code and inspect main.h for the LED's names. These snippets assume LD2_GPIO_Port and LD2_Pin; substitute the actual generated labels if different. Keep edits inside generator-preserved USER CODE regions. The following is only the body of the generated infinite loop, reached after HAL_Init(), clock setup, and MX_GPIO_Init():

HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin);
HAL_Delay(500);

Build, launch the project's ST-LINK debug configuration, and resume after any initial breakpoint. LD2 should change state every half-second: one complete on/off cycle takes approximately one second. This blocking delay is acceptable for proving the board and toolchain, but the loop cannot service another task during the wait.

Checkpoint: count about ten complete cycles in ten seconds. Change the delay to 1000 milliseconds, rebuild, and reprogram. The full cycle should now take about two seconds. That deliberate difference proves the board received your new build.
SECTION 03

A heartbeat without waiting

Replace the blocking loop body with a tiny time-driven state machine. First put this declaration in the preserved user-code region after generated initialization, before the infinite loop:

uint32_t last_toggle = HAL_GetTick();

Then use this loop-body snippet instead of the earlier toggle-and-delay pair:

uint32_t now = HAL_GetTick();
if ((uint32_t)(now - last_toggle) >= 500U) {
    last_toggle = now;
    HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin);
}
/* Other short, nonblocking work can run here. */

The LED's current output is its state. With the default HAL millisecond timebase, unsigned subtraction handles the 32-bit tick's wraparound, provided checks remain frequent and delays do not span a full counter cycle. >= avoids missing a deadline when the loop skips the exact millisecond. Setting the timestamp to now avoids catch-up bursts but allows drift; this is a heartbeat, not a precision scheduler.

Optional extension: read B1 with HAL_GPIO_ReadPin() and choose a faster interval while held. Configure PC13 as an input, inspect its schematic and pull configuration, and explicitly define a verified BUTTON_PRESSED_LEVEL. Do not assume pressed means low. Debounce before making a single press toggle a mode.

SECTION 04

Make the result repeatable

  • Build with no errors; confirm the selected board and programmed ELF.
  • Observe ten heartbeat cycles, then verify your deliberate timing change.
  • Resume execution, disconnect the debug session, and press reset. Confirm blinking restarts.
  • Reconnect USB with the normal power configuration; confirm the stored program runs again.

No blink? Check the data cable, power jumpers, ST-LINK detection, and programming result first. Confirm execution is not halted at a breakpoint. Inspect clock initialization, GPIO peripheral-clock enable, PA5 output mode, pin labels, and LED active level. If delays never finish, check that the HAL tick advances. Debug reset behavior can differ from a physical reset.

A multimeter can check low-voltage board power or a slowly held GPIO level against board GND; avoid shorts and never probe mains. UART logging is optional, not required evidence of success. See build, flash, and debug if the programming path is unclear.

Self-check: why does a 500-millisecond toggle produce a one-second cycle? What work can now run between transitions? Explain why power, programming, and execution are three separate checks.
