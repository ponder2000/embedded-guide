SECTION 01

A deadline for making progress

A watchdog is a timer that requests recovery—usually a reset—unless firmware refreshes it according to its rules. It can help recover from a deadlock or runaway loop. It cannot prove that the application is correct.

Begin with startup, clocks, and your first board project. Recovery is a complete path: detect a failure, reset, establish safe outputs, inspect the cause, and decide whether normal operation should resume.

For STM32F401, an independent watchdog and a window watchdog have different clocks and constraints. Read the exact reference manual and errata rather than transferring settings from another STM32 family.

SECTION 02

Feed only after evidence

An unconditional refresh inside a periodic ISR can hide a dead main loop. Instead, define the useful work that must complete: for example, the sensor pipeline advances and the control calculation finishes with valid inputs. A supervisor checks fresh evidence for each required activity in the current health window, then refreshes only if all required conditions hold.

Clear or advance the evidence for the next window so an old success cannot authorize refresh forever. Use sequence counters, timestamps, or bounded acknowledgements with appropriate synchronization. A flag that never gets cleared is not continuing proof of health. Do not require an event-driven task to produce an event when none was expected: define what healthy idleness means.

Choose a meaningful deadline: it must tolerate legitimate worst-case startup and execution delays yet recover before the system's maximum acceptable failure time. A 100 ms heartbeat does not automatically justify a 100 ms watchdog timeout.

If the watchdog clock varies with voltage or temperature, calculate both the shortest and longest possible timeout from the documented bounds. A window watchdog can reject an early refresh as well as a late one. Check whether sleep, debug halt, and reset change its behavior.

SECTION 03

Reset is not automatically safe

On startup, establish safe outputs before enabling actuators or resuming external communication. Some pin states are determined by reset defaults and external components before firmware runs. If failure could injure someone or damage equipment, a software watchdog is not a substitute for an engineered hardware safety mechanism.

  • Capture reset-cause flags early, before code clears them; distinguish watchdog, power, and software reset where the MCU supports it.
  • Ensure settings and persistent records tolerate interruption. A reset in the middle of a flash write can leave incomplete data.
  • Plan for repeated resets: safe mode, bounded retries, or a latched fault may be better than an endless reboot loop.
  • Avoid writing flash on every boot or refresh; account for endurance and power-failure behavior.

Some watchdogs cannot be stopped after being enabled until reset; option bytes can also enable them automatically. Read the programming and recovery procedure before changing those settings. This lesson intentionally gives no portable register-enable sequence.

SECTION 04

Prove the failure path

Use a safe bench setup with actuators disconnected. Inject a stall in foreground work while interrupts still run: a properly supervised refresh should stop and recovery should occur. Then omit a required health acknowledgement and verify the same outcome. Confirm reset cause, boot behavior, and safe output states after each test.

Also run legitimate long operations and startup sequences to check for false resets. Repeat the tests without a debugger; debug freeze settings can completely change watchdog behavior. Measure the observed failure-to-recovery interval rather than assuming the configured nominal timeout is the entire recovery time.

Official reference: the STM32F401RE documentation includes RM0368, its datasheet, and errata. Consult watchdog, reset/clock control, power, and debug-freeze sections together.
